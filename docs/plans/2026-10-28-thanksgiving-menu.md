## How booking works
Nothing new on the payment side. Each seating is its own Director class. On each date, the classes in `public_site_schedule` that start before 1pm are sorted by start time and fill that morning's seatings in order (`data-tg-seat` 0, 1, 2 in index.html; Friday has three). "Reserve a seat" puts that class in the same drop-in cart, and it checks out through the same `drop-in-checkout` Stripe flow as the chips. Price, spots and Full all come from the Director class, so the server stays the authority on money. Those rows are kept out of the weekly lists so nothing shows up twice: the class list and the full ProSeries week on /schedule/ (js/schedule.js), the DROP IN panel on Home and ProSeries (js/now.js), and `scripts/check-classes-jsonld.mjs`. All of them read one rule from the card's own markup: a class on a `data-tg-date` day that starts before the section's `data-tg-before` ("13:00") is a menu class. Delete the card and the rule goes with it. The ProSeries track weeks (js/tracks.js) need no rule: they only count rows with a track_label, and these have none. If a morning ever gets a different number of classes than the card has seatings, the extra class has no button and a missing one leaves its seating on "Reservations open soon", so the card and the Director must change together.

Button states per seating: no class or not open for drop-in = "Reservations open soon" (disabled); open = price + "Reserve a seat"; in the cart = "In your order"; `spots_left` 0 = "Fully booked"; after the class starts = "Served". Open with no fee set reads "Price TBA". After Nov 27 (New York time) the whole block hides. One order holds six classes at most (the cart's limit), so a family booking all seven seatings checks out twice.
